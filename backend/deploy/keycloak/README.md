# Keycloak для CRM ИТ Школы

Вход в CRM по ТЗ (п. 10 функциональных требований) — через Keycloak. Здесь всё, что нужно, чтобы он заработал сразу:

| Файл | Что это |
| --- | --- |
| `realm-it-school.json` | Realm `it-school`: роли, группы, клиенты, пользователи и политики безопасности. Импортируется при первом старте. |
| `run-local.sh` | Запуск без Docker: скачивает Keycloak 26.7.4, импортирует realm, поднимает на `http://localhost:8080`. |
| `init-keycloak-db.sql` | Отдельная база `keycloak` в PostgreSQL для `docker-compose.yml`. |

## Запуск

Без Docker (нужна Java 21; macOS: `brew install openjdk@21`):

```bash
backend/deploy/keycloak/run-local.sh
```

В Docker Compose Keycloak поднимается вместе с API и PostgreSQL: `cd backend && docker compose up -d --build`.

Консоль администратора: <http://localhost:8080/admin> — `admin` / `admin` (только для локального стенда).

## Что внутри realm

**Роли** (ролевая модель ТЗ, п. 11) — приложение понимает и эти имена, и синонимы `manager` / `lead`:

| Роль Keycloak | Роль в CRM | Группа |
| --- | --- | --- |
| `kam` | Менеджер (пользователь, КАМ) | «Менеджеры по вузам» |
| `manager_lead` | Руководитель | «Руководители» |
| `admin` | Администратор | «Администраторы» |

Роль выдаётся через группу: чтобы сделать сотрудника руководителем, достаточно добавить его в группу.

**Клиенты:**

- `rtk-it-school-web` — браузерное приложение. Публичный клиент, Authorization Code + PKCE (S256), без секрета; прямой вход по паролю и implicit flow выключены.
- `rtk-it-school-api` — получатель токенов (audience). API принимает только токены, выписанные для него (`KEYCLOAK_AUDIENCE=rtk-it-school-api`).

**Пользователи** — те же, что в демо-данных CRM, с теми же `id` и почтами, поэтому вход сразу привязывается к карточке сотрудника. Пароль у всех: `ItSchool-2026!`

## Безопасность (152-ФЗ, приказ ФСТЭК № 117)

- Пароль: не короче 12 символов, заглавные и строчные буквы, цифра, спецсимвол, не совпадает с логином и почтой, последние 5 паролей не повторяются, смена раз в 90 дней.
- Защита от подбора: после 5 неудачных попыток — временная блокировка, до 15 минут.
- Короткие токены: доступ — 5 минут, сессия гаснет через 30 минут бездействия и через 10 часов в любом случае.
- Журналы: события входа и выхода, ошибки, смена паролей хранятся 180 дней; действия администраторов — с деталями.
- Самостоятельная регистрация выключена: учётные записи заводит администратор.
- Для администраторов рекомендуем включить второй фактор: *Authentication → Required actions → Configure OTP* (политика TOTP уже настроена).

## Как добавить сотрудника — прямо в CRM

Учётные записи создаются в разделе **«Пользователи и доступ»**; в Keycloak заходить не нужно — CRM сама вызывает его Admin API через служебный клиент `rtk-it-school-admin` (права только на пользователей: `manage-users`, `view-users`, `query-users`, `query-groups`).

1. Администратор (или руководитель — для своей команды) нажимает **«Добавить сотрудника»**: имя и фамилия, рабочая почта, при желании логин; администратор выбирает роль, руководителя и какие вузы видит сотрудник.
2. CRM создаёт пользователя в Keycloak, кладёт его в группу нужной роли и показывает **временный пароль** — один раз, с кнопкой «Скопировать». Его нужно передать сотруднику лично.
3. Сотрудник входит через «Войти через Keycloak» — Keycloak сразу просит задать свой пароль (по политике realm). После этого он попадает в CRM со своей ролью.

Дальше в той же таблице:

| Действие | Кто может | Что происходит |
| --- | --- | --- |
| Сменить роль | администратор | группа в Keycloak и роль в CRM меняются вместе; свою роль сменить нельзя |
| Заблокировать / разблокировать | администратор; руководитель — своих менеджеров | учётка в Keycloak отключается, активные сессии завершаются, в CRM — «Заблокирован» |
| Выдать временный пароль («⋯») | администратор; руководитель — своих менеджеров | новый пароль с обязательной сменой при входе |
| Видимость данных, направления, руководитель | администратор | хранится в CRM |

Каждое действие записывается в «Журнал действий» CRM, а в Keycloak — в журнал административных событий.

API: `GET /api/v1/accounts/status`, `POST /api/v1/accounts`, `PUT /api/v1/accounts/{id}/role`, `PUT /api/v1/accounts/{id}/status`, `POST /api/v1/accounts/{id}/password` (описаны в Swagger). Настройки API: `KEYCLOAK_ADMIN_CLIENT_ID`, `KEYCLOAK_ADMIN_CLIENT_SECRET` (секрет — в `realm-it-school.json`), `KEYCLOAK_ADMIN_URL` — если API ходит к Keycloak по внутреннему адресу (Docker). Без этих настроек карточки создаются только в CRM, и страница об этом предупреждает.

## Продуктив

- Задайте свой домен: `--hostname=https://sso.<домен>` и адреса возврата клиента `rtk-it-school-web` (`https://crm.<домен>/*`).
- Смените пароль `admin` (`KC_BOOTSTRAP_ADMIN_PASSWORD`), секрет клиента `rtk-it-school-admin` (*Clients → Credentials → Regenerate*, затем `KEYCLOAK_ADMIN_CLIENT_SECRET`) и пароли демо-пользователей — или удалите их из `realm-it-school.json` перед первым запуском.
- Запускайте `kc.sh start` (не `start-dev`) за HTTPS-прокси и с `sslRequired: external` (уже задано).
- API: `KEYCLOAK_ISSUER_URL` — публичный адрес realm (он же `iss` в токене), `KEYCLOAK_JWKS_URL` — внутренний адрес ключей, если API ходит к Keycloak по внутренней сети.
